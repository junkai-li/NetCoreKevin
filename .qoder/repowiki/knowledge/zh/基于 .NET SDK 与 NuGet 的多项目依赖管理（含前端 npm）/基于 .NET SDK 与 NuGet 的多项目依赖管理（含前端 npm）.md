## 1. 使用的系统与工具

本仓库采用 **双栈依赖管理**：
- **.NET 后端**：使用 .NET SDK（目标框架 `net9.0`）+ **NuGet**，通过每个 `.csproj` 中的 `<PackageReference>` 声明第三方包；项目间通过 `<ProjectReference>` 引用 kevin 框架下的子模块。
- **Vue3 前端**：位于 `vue/kevin.web.vue/`，使用 **npm** + **Vue CLI 5**，依赖声明在 `package.json`，锁定版本由 `package-lock.json` 提供。

仓库根目录没有全局的 `Directory.Packages.props`、`global.json`、`nuget.config`、`packages.lock.json`、`go.mod`、`vendor/` 等集中式或锁文件形式的依赖管理配置，因此依赖版本以各工程内 `.csproj` / `package.json` 为准。

## 2. 关键文件

- `.csproj` 清单（示例）：
  - `App/WebApi/App.WebApi.csproj`：WebApi 入口，仅引用少量 NuGet 包（如 `Microsoft.EntityFrameworkCore.Design`、`Microsoft.VisualStudio.Azure.Containers.Tools.Targets`），并通过 `ProjectReference` 指向 `App.Application`。
  - `Kevin/Domain/kevin.Domain.csproj`：核心领域层，引入 `Microsoft.AspNetCore.Authentication`、`Microsoft.EntityFrameworkCore.Abstractions`、`Microsoft.Extensions.DependencyInjection`、`System.Formats.Asn1`，并引用 `kevin.Module` 下的多个子模块。
  - `Kevin/kevin.Module/Kevin.Common/Kevin.Common.csproj`：通用基础库，集中声明大量第三方包（阿里云 SDK、AutoMapper、Mapster、MySqlConnector、NPOI、ImageSharp、SkiaSharp、Selenium、Tesseract、PDF 解析等）。
  - `Kevin/kevin.Module/kevin.AI.AgentFramework/kevin.AI.AgentFramework.csproj`：AI Agent 框架，声明 `Microsoft.Agents.AI.*`、`ModelContextProtocol`、`OpenTelemetry*` 等 AI/可观测性相关包。
  - `Test/Kevin.Web.Test/Kevin.Unit.Tests.csproj`：测试工程，声明 xUnit、coverlet、Microsoft.NET.Test.Sdk 等测试依赖。
- 前端依赖清单：
  - `vue/kevin.web.vue/package.json`：声明 Vue3、Ant Design Vue、axios、codemirror、@microsoft/signalr 等运行时依赖以及 @vue/cli-service、eslint、webpack 等开发依赖。
  - `vue/kevin.web.vue/package-lock.json`：npm 依赖锁定文件。
- 解决方案与容器：
  - `NetCoreKevin.sln`：聚合所有 .NET 项目的解决方案文件。
  - `docker-compose.yml`、`App/WebApi/Dockerfile`：用于将构建产物打包为镜像，间接依赖 .NET SDK 与 Node 环境。

## 3. 架构与约定

### 3.1 分层与模块化依赖
- 后端按 `App`（业务应用）和 `Kevin`（框架/模块）两大目录组织，其中 `Kevin/kevin.Module` 下包含约 20 个独立 NuGet 风格的子项目（如 `Kevin.Ioc`、`Kevin.Cache`、`Kevin.RabbitMQ`、`Kevin.SignalR`、`Kevin.Hangfire`、`Kevin.Consul`、`Kevin.FileStorage`、`Kevin.Permission`、`kevin.AI.AgentFramework` 等），每个子项目都是一个独立的 `.csproj`，对外暴露服务扩展方法（常见 `ServiceCollectionExtensions` 类）。
- 依赖方向遵循“上层依赖下层”的分层约定：`App.WebApi` → `App.Application` → `App.Domain` / `App.RepositorieRps` → `Kevin.*` 模块；`Kevin.Domain` 再反向引用 `kevin.Module` 下的能力模块。这种结构使得每个模块可以单独作为 NuGet 包发布（虽然当前未看到 `.nuspec` 或 CI 打包脚本）。

### 3.2 包版本管理方式
- **无集中式版本管理**：未发现 `Directory.Packages.props`、`Directory.Build.props`、`global.json`、`NuGet.Config` 或 `packages.lock.json`，各 `.csproj` 直接写死版本号（例如 `Microsoft.EntityFrameworkCore` 系列为 `9.0.11`，`Newtonsoft.Json` 为 `13.0.4`，`xunit` 为 `2.5.3`）。
- **跨项目版本对齐是约定而非强制**：从已查看的几个 `.csproj` 可见 EF Core、Microsoft.Extensions.*、xUnit 等常用包在不同项目中使用了相同主版本，但这是人为维护的结果，不是由 MSBuild 或 NuGet 自动保证的。
- **前端使用 npm 锁定**：`vue/kevin.web.vue/package-lock.json` 会锁定具体子依赖版本，配合 `package.json` 中较宽泛的版本范围（如 `^4.2.6`、`^1.17.0`）实现可复现构建。

### 3.3 私有源与认证
- 仓库中未发现 `NuGet.Config`、`~/.nuget/NuGet/NuGet.Config`、`NUGET_CREDENTIAL_PROVIDER`、`NUGET_AUTH_TOKEN` 等私有 NuGet 源或凭据配置；也未发现 `pnpm-workspace.yaml`、`.npmrc`、`yarn.lock` 等 npm 私源配置。
- 这意味着当前依赖来源默认是 nuget.org 和公共 npm registry，若需接入企业私有源，需要额外添加配置文件。

### 3.4 本地化/平台特定依赖
- 部分包通过条件编译或平台包形式处理：例如 `Emgu.CV.runtime.ubuntu-x64`、`Emgu.CV.runtime.windows`、`SkiaSharp.NativeAssets.Linux`、`Selenium.WebDriver.MSEdgeDriver`，这些属于运行时原生依赖，由 NuGet 在安装时根据目标平台拉取。
- Docker 构建通过 `Dockerfile` 指定 .NET SDK 镜像，Node 构建通过 `vue/kevin.web.vue` 下的 npm 流程完成，两者都依赖宿主机的网络访问公共源。

## 4. 约定与约束

- **目标框架统一为 `net9.0`**：所有已查看的 `.csproj` 均设置 `<TargetFramework>net9.0</TargetFramework>`，形成统一的运行时基线。
- **包版本以 `.csproj` 中显式声明为准**：不存在版本提升策略或通配符升级机制，新增/升级包需要在对应 `.csproj` 中修改 `<PackageReference Version="..." />`。
- **项目间解耦通过 `ProjectReference` 而非 NuGet 包发布**：当前 kevin 模块之间全部以源码引用方式组合，便于单仓开发调试；若要对外分发，需补充打包流程。
- **前端依赖通过 `package.json` + `package-lock.json` 管理**：新增/升级前端依赖应修改 `vue/kevin.web.vue/package.json` 并由 npm 生成新的 lock 文件。
- **未见强制的依赖安全扫描或许可证检查**：仓库中没有看到 `dotnet audit`、`npm audit`、`license-checker` 等 CI 步骤，也没有 `.github/workflows` 或 Azure DevOps 管道定义来强制执行依赖治理规则。
- **Docker 忽略项**：`.dockerignore` 排除了 `node_modules`、`bin`、`obj`、`.vs` 等目录，避免把本地依赖缓存打入镜像，符合常规最佳实践。

总结：该仓库是一个典型的多项目 .NET 9 + Vue3 工程，依赖管理以“每个工程各自声明 NuGet/npm 依赖”的方式实现，缺乏集中式版本管控、私有源配置和自动化升级/审计流程；其优势是结构简单、易于本地开发，风险在于跨项目包版本一致性依赖人工维护。
