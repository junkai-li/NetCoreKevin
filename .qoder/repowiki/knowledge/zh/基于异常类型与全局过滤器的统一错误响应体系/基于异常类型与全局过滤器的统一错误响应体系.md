## 1. 整体方案

该 .NET 企业级 AI 中台采用 **自定义异常 + ASP.NET Core 全局异常处理中间件 + MVC 结果过滤器** 的组合方式，实现统一的错误定义、传播与 HTTP 响应封装。业务层通过抛出特定异常表达错误，由框架在管道末端统一捕获并转换为一致的 JSON 结构 `{ code, IsSuccess, msg, errMsg }`。

## 2. 核心文件与职责

- `Kevin/kevin.Share/FieldValidationException.cs`：字段校验失败时抛出的领域异常基类，继承 `Exception` 并支持消息模板参数化构造。
- `Kevin/kevin.Module/Kevin.Common/App/Global/GlobalError.cs`：全局异常处理器，通过 `IExceptionHandlerFeature` 捕获未处理异常，记录日志（`Kevin.log4Net.LogHelper<Exception>.logger.Error`），并根据异常类型决定 HTTP 状态码与响应体。
- `App/WebApi/Program.cs`：在 `UseExceptionHandler` 中注册 `GlobalError.ErrorEvent`；开发环境使用 `UseDeveloperExceptionPage`，生产环境走全局错误处理。
- `Kevin/Kevin.Web.Basics/Filters/ResultFilter.cs`：MVC 输出结果过滤器，对非文件流返回做统一包装：将 `400/401/500` 等状态码映射为统一 JSON，正常路径包装为 `{ code: 200, msg: "success", IsSuccess: true, data }`，并对返回值中的 null string/List 做递归空值填充（最大深度 128 防止栈溢出）。
- `Kevin/Domain/Auth/ApiResponseHandler.cs`：自定义 `AuthenticationHandler`，重写 `HandleChallengeAsync` / `HandleForbiddenAsync`，将 401/403 认证/授权失败以统一 JSON 格式返回。
- `Kevin/Kevin.Web.Basics/Extensions/ServiceConfiguration.cs`：在 `AddMvc` 中注册 `ResultFilter`、`HttpLogFilter`、`TransactionScopeFilter` 等全局过滤器。
- `Kevin/kevin.Module/Kevin.Common/App/Http/StatusCodes.cs`：集中定义 HTTP 状态码常量，供各层引用。

## 3. 架构与约定

### 3.1 异常分层
- **业务可预期错误**：Application/Domain 服务中抛出 `UserFriendlyException`（来自外部 kevin 基础库），例如“数据不存在或已删除”“智能体名称已存在”。这类异常被 `GlobalError` 识别后降级为 `400 Bad Request`，并将 `InnerException.Message` 作为 `errMsg` 返回。
- **字段校验错误**：抛出 `FieldValidationException`，同样被 `GlobalError` 识别并按 400 返回。
- **系统内部异常**：未被捕获的任意 `Exception` 走默认分支，返回 `500 Internal Server Error`，同时把请求 path、参数、Authorization 头与异常堆栈序列化到日志。

### 3.2 管道顺序
```text
Request → UseExceptionHandler(GlobalError) → Authentication(401/403) → Authorization → Controller → ResultFilter(统一包装) → Response
```
- 认证失败由 `ApiResponseHandler` 直接写回 JSON 并设置状态码，不经过 `ResultFilter`。
- 控制器返回的普通对象经 `ResultFilter` 包装；若控制器显式设置 `400/401/500`，则按对应分支写入统一错误体。

### 3.3 统一响应结构
成功：
```json
{"code":200,"msg":"success","IsSuccess":true,"data":...}
```
失败：
```json
{"code":400/401/500,"msg":"errmsg","IsSuccess":false,"errMsg":"具体错误信息"}
```

## 4. 约定与约束

- **业务层禁止吞掉异常**：应用层服务普遍直接 `throw new UserFriendlyException(...)`，不在方法内 try-catch 包裹，交由全局管道处理。
- **HTTP 状态码必须通过异常或显式设置**：控制器不应手动 `context.Response.StatusCode = ...` 再返回裸字符串，应依赖 `ResultFilter` 统一包装。
- **认证/授权失败不走业务异常**：由 `ApiResponseHandler` 固定返回 401/403 的中文提示，避免业务代码重复处理鉴权错误。
- **日志记录位置**：所有未处理异常均通过 `Kevin.log4Net` 记录，包含请求上下文与完整堆栈；`GlobalError` 中对大请求体做了 102400 字节截断以防日志爆炸。
- **返回值空值规范化**：`ResultFilter` 递归将返回对象中 `string` 类型的 null 替换为空串、`List<T>` 类型的 null 替换为空集合，保证前端稳定消费。
- **递归保护**：`ResultFilter` 内置 `MaxRecursionDepth = 128`，超过深度即停止反射遍历，避免深层嵌套导致性能问题或栈溢出。

## 5. 已知缺口

- 项目中未见统一的错误码枚举（如 `ErrorCode.NotFound`），错误信息以硬编码中文消息为主，后续可扩展错误码表以便前端国际化。
- `FieldValidationException` 仅承载消息，未携带字段名列表，无法直接生成结构化校验错误响应。
- 部分第三方调用（如 `RemoteFileDownloader`、`AliCloudAsrService`）直接使用 `response.EnsureSuccessStatusCode()` 抛出 `HttpRequestException`，这些异常最终会被 `GlobalError` 兜底为 500，但缺少更细粒度的分类。
